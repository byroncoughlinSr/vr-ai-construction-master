# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

End-to-end pipeline that turns a spoken prompt into a walkable VR house on Meta Quest 2/3:
voice → Whisper transcription → LLM construction plan → Stable Diffusion rendering →
3D geometry → Meta Spatial entities the user walks through. Three deployable parts talk over
HTTP/WebSocket; there is no shared code between them — the contract is the JSON on the wire.

```
construction-quest (Kotlin/Quest)  ──HTTP/WS──►  backend-core/backend (FastAPI)  ◄──HTTP──  backend-core/dashboard (Vue 3)
```

- Backend server: `http://192.168.4.249:8000`  (LAN IP — the Quest must reach this, not localhost)
- Dashboard dev server: `http://localhost:3001` (Vite binds `0.0.0.0`; the Quest loads it by LAN IP)
- WebSocket base: `ws://192.168.4.249:8000/api/v1/ws`

## Commands

### Backend (`backend-core/backend`)
```bash
./start_all.sh                    # from repo root: backend (:8000, log → backend/backend.log) + dashboard (:3001); Ctrl+C stops both
./restart_backend.sh              # from repo root: kills port 8000, activates venv, runs uvicorn --reload
source venv/bin/activate          # the venv lives in backend-core/backend/venv
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload   # manual run (must bind 0.0.0.0 so Quest can reach it)
pytest                            # all backend tests
pytest tests/test_api.py          # one file
pytest tests/test_api.py::test_name   # one test
alembic revision --autogenerate -m "msg"  # new migration
alembic upgrade head                      # apply migrations (the backend also runs them on startup)
python -m scripts.seed_example_floor_plan # migrate + add the example house "Maple Hollow Cottage"
docker compose up -d postgres pgadmin   # DB only — the backend container would take port 8000 from
                                        # the native uvicorn (docker-compose.prod.yml has profiles)
```
There is no `pytest.ini`/`conftest.py` — run `pytest` from `backend-core/backend` with the venv
(Python 3.12, full `requirements.txt`) active. Tests use in-memory SQLite: each test module installs
its `get_db` override in a fixture and removes it afterwards — don't set `app.dependency_overrides`
at import time, or modules clobber each other's database. `app/services/__init__.py` imports lazily,
so `vr_geometry_service` loads without torch; `test_vr_geometry.py` and `test_planning_service.py`
make no network calls. `test_compel_integration.py` needs a GPU and real models (its async tests are skipped).
Tests of plan-backed routes start a real pm-mcp server once per run (`tests/pm_server.py`, `use_pm()`; skipped
when `/development/pm-mcp/.venv/bin/pm-mcp` or `PM_MCP_COMMAND` is missing). That server outlives each test's
database, so give test projects `unique()` names.
Config comes from `.env` (copy `.env.example`); `app/config.py` is the Pydantic settings source of truth.

**LLM provider chain** (`ai_planning_service.py`, in priority order):
1. **Groq** — the primary planner. `GROQ_API_KEY` + `GROQ_MODEL` (default `openai/gpt-oss-120b`),
   called with `response_format={'type':'json_object'}`.
2. **Ollama** — fallback. Runs **natively, not in Docker** (Docker Ollama was OOM-killed); model
   `OLLAMA_MODEL=llama3.1:8b` exactly; `OLLAMA_URL=http://localhost:11434` when uvicorn runs natively
   (the Docker bridge IP only when the backend is containerised). Unlike Groq/Gemini, Ollama is re-probed
   (3 s timeout) at most every 30 s while down, and only when the chain reaches it, so starting it
   (`sudo systemctl start ollama`) needs no backend restart.
   See `QUICK_START.md` / `NATIVE_OLLAMA_SETUP.md`.
3. **Gemini** — last-resort fallback, `GEMINI_API_KEY`.

A missing key silently demotes to the next provider. Groq's JSON mode sometimes rejects a long plan
(`json_validate_failed`) over a stray quote and miscounted braces around `"rooms"`; `_generate_with_groq`
repairs the rejected `failed_generation` (`_salvage_groq_json`) and, if that fails, asks Groq once more.
The on-demand tier allows 8,000 tokens per minute **counting `max_tokens` (4096)**, and a refine prompt for a
12-room house is ~4,000+: a 413 is retried once with `max_tokens` cut by the overrun + 256 (`_groq_tokens_over`).
Keep the refine prompt and `site_summary` lean — anything added there eats into the answer.
The chain moves on when a provider errors, times out, **or returns output that can't be parsed into a plan**; all of it shares one `PLANNING_TIMEOUT_SECONDS`
budget (200 s, below the headset's 240 s `PLAN_CALL_TIMEOUT_S`). The log line `🧠 Plan generated by <name>`
says which planner actually ran.

## Architecture

### Backend — FastAPI (`backend-core/backend/app`)
- `main.py` mounts all routers under `/api/v1/*` and wires middleware (rate limiting via slowapi,
  CORS, gzip, request-ID logging). Router prefixes: `image`, `planning`, `projects` (two routers:
  `projects.py` and `project_controls.py`), `designs`, `materials`, `resources`, `crm`, `assistant`,
  `plants`, `furniture`, `voice`, `ws`.
- `api/v1/` = HTTP/WS surface; `services/` = the actual AI + geometry logic; `models/` SQLAlchemy,
  `schemas/` Pydantic. Routes stay thin and delegate to services.
- **AI services** (`services/`): `ai_planning_service.py` (Groq→Ollama→Gemini → phases, tasks,
  materials, cost, timeline, image prompt), `ai_image_service.py` (Stable Diffusion + compel,
  CUDA when available else CPU), and `vr_geometry_service.py` (rooms → floor/wall/ceiling/door/window
  vertices).
- **Never trust raw LLM output as JSON.** `ai_planning_service.py` runs everything through
  `_parse_structured_plan` → `_extract_and_repair_json` / `_clean_json_string`: it strips code fences,
  fixes trailing/missing commas and Python literals, and closes truncated objects/arrays. If you add a
  provider or change the plan schema, route it through that pipeline. Strategy 1 parses the extracted JSON
  **as-is first** and only runs the regex repairs (`_clean_json_string`) if that fails — the repairs work
  on raw text and corrupt valid strings (`"Bedroom 2"` → `"Bedroom 2,"`). Background in `JSON_PARSING_FIX.md`.
- **Image generation** (`ai_image_service.py`): one shared pipeline (`get_image_service()`), one generation
  at a time behind an `asyncio.Lock`. Compel runs with `truncate_long_prompts=False` and pads the
  prompt/negative embeddings to the same length, so long voice descriptions are not cut at 77 tokens.
  `POST /image/generate` bounds width/height (256–1024, multiple of 8), steps (1–100) and guidance.
  Background jobs go through `image_jobs.start_image_generation` → `background.run_in_background`
  (holds a strong task reference); results/errors are kept 15 min for late WebSocket clients.
- DB is PostgreSQL via SQLAlchemy 2.0; migrations with Alembic (`alembic.ini`, `alembic/`). Migrations are the
  only thing that creates tables; revision `9a4e6c1f2b83` rebuilt the budget/permit/inspection/document tables,
  which the initial migration had created with an older layout than the models. After changing a model,
  autogenerate a migration and check `compare_metadata` comes back empty.
- **Floor plans** (`models/floor_plan.py`, `services/floor_plan_service.py`): the `floor_plans` table holds
  versioned plans per project — `name` (the house name), `layout` tree and `rooms` (feet), `change_type`
  (`generated` / `edited` / `refined` / `example`), `change_note`, `source`, and the accepted `image_url`.
  Every change inserts the next version; the highest is current and is what `GET /projects/{id}/generate-vr`
  builds (via `geometry_for_project`, which falls back to the old `ai_generations` plan, then phase names, for
  projects without one). Geometry carries `floor_plan: {id, version, name, image_url}`. Routes:
  `GET /projects/{id}/floor-plan(s)`, `PUT /projects/{id}/floor-plan` (dashboard edit; renames the project
  too; 422 if unbuildable), `POST /projects/{id}/floor-plan/refine` (`{instruction}` → planner chain via
  `refine_floor_plan`, prompt in `_build_refine_prompt` — keep it in step with `_build_planning_prompt`;
  the AI answers with a `scope`: an `"exterior"`-only change updates the current version **in place**
  (`updated_in_place: true`), a room change adds a version),
  `PUT /projects/{id}/floor-plan/image` (link an accepted render). `ai_generations.source` now records the
  real provider (it used to default to "ollama"). The example plan lives in `services/example_floor_plans.py`.

### VR geometry — the cross-language contract that breaks silently
`vr_geometry_service.py` builds the JSON that `HouseGenerator.kt` turns into 3D boxes. Three
constants **must** stay in sync across the language boundary or the house develops visible seams:
- `WALL_T = 0.1` (half wall thickness) must equal `WALL_HALF_THICKNESS_M = 0.1f` in `HouseGenerator.kt`.
  Every Kotlin box goes through `centeredBox(size)` (`Boxes.kt`): the SDK's `Box(min, max)` takes two
  corners, and passing one vector puts the box beside its entity instead of around it.
- `FT_TO_M = 0.3048` — the AI returns dimensions in **feet**; the VR world is **metres** (1 unit = 1 m).
  Conversion happens backend-side; Kotlin consumes metres directly.
- `SCALE = 1.0f` in `HouseGenerator.kt` (real size; it was 2, which looked twice life size in the headset
  however high the eyes were put) — **every** position, dimension and spawn point from the JSON is
  multiplied by it on the Kotlin side. Anything you add to the geometry JSON must be scaled too, or it
  lands at the wrong size / distance if SCALE ever changes again.

**Layout is a nested-split tree** the AI returns as `project_structure.layout`: a footprint
(`length` along x, `width` along z, street side at z = 0) recursively divided by `"split": "x"|"z"` into
`parts`, each with a relative `size` and either a `room` name, `"open": true` (outdoors: how the house
gets an L/U/T shape, a courtyard or an inset porch) or another split (`layout_rects_from_tree`; open
parts via `layout_open_rects`). Part sizes are rescaled to fill their parent, with a `MIN_PART` floor, so
rooms and open parts always tile the footprint with no gaps or overlaps. Walls facing an open part count
as exterior (windows, front door); the geometry lists open parts as `open_areas` (the dashboard draws them
as "Outside"), and the spawn point stops halfway across one if a room is on the far side. `project_structure.rooms` then only supplies
height, materials and `connects_to`. `layout.entry` names the room that gets the front door (it becomes
room id 1). The prompt in `_build_planning_prompt` describes this format — change both together.
If the tree is missing or malformed (`LayoutError`), it falls back to the old grid:
`compute_packed_positions` packs rooms 3 per row in list order, rows share their max depth, and room 0
is the entry. `geometry.metadata.layout` says which one ran (`"split"` / `"grid"`).

Doorways (`plan_connections`): a requested connection becomes a door only if the two rooms share at
least `DOOR_W + 2·EDGE_MARGIN` of wall (`find_shared_walls`); then doors are added until every room is
reachable from the entry, preferring hallways/living spaces. Those added doors are in no room's `connects_to`,
so a room's `no_door_to` (names) is what removes one: blocked pairs are never requested and only added as a
last resort (with a `geometry.notes` entry); `site_summary` gives the refine prompt every real doorway. The front door goes on the entry's outside
wall (street side first, then sides, then back) and `spawn_position` is 3 m outside it. Windows go on the longest exterior stretch
(none in hallways/closets, small ones in bathrooms). Openings are **cut out of the walls backend-side**:
every wall on the opening's line (i.e. both rooms' walls) is split into pieces around it, and each
piece's `start.y` is its base height (0, or the door/window top for headers). Rotation values are sent in
**degrees** in the JSON, measured as `atan2(dz, dx)` (0 = along x, 90 = along z). The SDK's yaw turns
+x toward `(cos θ, −sin θ)`, so `HouseGenerator.kt` builds every rotation through `yawAlong(deg)`, which
negates it; at 0/90° the sign is invisible, but diagonal walls (angled bay windows) come out mirrored
without it.

**Bay windows**: a room in the plan may carry `"bay_window": {side: front|back|left|right, width, depth
(ft), style: angled|box}` (`bay_spec`). `build_bay` puts it on the longest clear outside stretch of that
side (shrinking to fit beside the front door, never into another room or bay), cuts a full-height opening
in the room's wall, and adds the bump-out's walls (any angle, `_segment_wall`) with tall windows
(`"bay": true`, replacing the room's ordinary window). The room's `bay_window` in the geometry has the
`outline` (dashboard) and its own `floor`/`ceiling` slabs (bounding box; an angled bay shows a small ledge
and eave), which `HouseGenerator.generateRoom` builds. A side with no outside wall is skipped.

**Doors to the yard**: a room may carry `"outside_doors": [{side, style: sliding_glass|french|hinged, width
(ft)}]` (`outside_door_specs`; fuzzy styles, `"rear"`/`"backyard"` → back). `place_outside_door` centres each
on the longest clear outside stretch of that side, narrowed to fit; they are placed after the front and
interior doors and before bays and windows, which keep clear of them. In the geometry they are doors with
`door_type: "patio"` plus `style`/`side` — the front door stays the only `"exterior"` one (`site_summary`,
the dashboard's "▲ Entry" and `HouseGenerator` rely on that). `HouseGenerator.generateDoorLeaves` draws them
left open (sliding panel over the fixed one, French leaves swung out). `site_summary` lists them as
`outside_doors` so a later "deck outside the sliding door" lands there. Requested doors and bay windows that
don't fit are listed in `geometry.notes`; the headset shows them after a refine, the dashboard under the plan.
The history of
seam/rotation bugs and the exact fixes is documented in `claude.md` (despite the name, it is a
fix-notes doc, not guidance) and `LOAD_TO_VR_FIX.md` — read these before touching geometry.

**Outside of the house** (`services/vr_exterior.py`, column `floor_plans.exterior`): `{roof: {style:
gable|hip|flat|shed, material, color, pitch, overhang}, walls: {material, color}, trim, ground, landscape:
[items]}`, sizes in feet, positions in layout coordinates (front yard is z < 0). `exterior_spec` cleans
what the AI sends (named colors → hex, fuzzy materials and plant names, unknown items dropped); the prompt
text is `EXTERIOR_FORMAT` in `ai_planning_service.py` — keep the two in step. New versions carry the
exterior over. `build_exterior` turns it into `geometry.exterior` in metres: `roof` triangle meshes (both
windings, flat normals; one roof per rectangle `roof_sections` can merge, eave on the tallest room, lower
rooms' finish runs up to it), and `parts` (boxes/spheres with `kind` wall | roof | ground | landscape): a
2 cm finish skin on outside wall faces with the same openings, ground at y = −0.10 m with a foundation
under each room, and paths/fences built from primitives. Plants come from `services/vr_plants.py`:
`find_species` matches the item's `plant` name against `SPECIES` (color words tint the flowers), and each
species' `form` builder makes a low-poly mesh of color groups; trees/shrubs are shared variants in a unit box
(`exterior.plant_meshes`, instanced by `exterior.plants` with position/scale/yaw), beds and hedges one baked
mesh each. Plants are nudged out of rooms. Nothing is stored but the description. `refine` gives the AI a
`site_summary` (rooms, front door, which way it faces and ready-made spots beside it, and the names of the
photo plant models). Headset side: `ExteriorBuilder.kt` (roof meshes via
`registerMeshCreator("mesh://exterior/N")`, plants through `MeshInstances.kt`; x-ray hides roof and finish).

**Plant models from photos** (`services/plant_model_service.py`, table `plant_models`, routes
`/api/v1/plants/models`, dashboard page `/plants` → `PlantsView.vue`): a named plant ("Coral rose") with a
photo, or a description that Stable Diffusion draws, is turned into a `.glb` in the background by
`PLANT_MODEL_PROVIDER` — `replicate` (hosted TRELLIS, needs `REPLICATE_API_TOKEN`, the photo leaves the
machine), `triposr` (local clone at `TRIPOSR_DIR`, minutes per model on CPU) or `none`. `normalize_glb`
makes every model stand 1 m tall on its origin; files live in `plant_models/<id>/` and are served at
`/plant_models/...` (outside `/api/v1`). Jobs only run in this process, so a restart marks pending ones
failed (Retry). `build_exterior` swaps a landscape item for a ready model when its name matches
(`_plant_model`, by `name_key`, or `model_id`) and lists it in `exterior.models` (`scale` = height in m);
`MeshInstances.buildModel` loads it from `SERVER_URL` + url. Deleting a model sends houses back to the
drawn plant. The same table holds furniture models (`kind` = `plant` | `furniture`; routes
`/api/v1/furniture/models`, dashboard page `/furniture`; both pages are `ModelLibraryView.vue`, and
`ready_models(db, kind)` keeps the two apart).

**Furniture** (`services/vr_furniture.py`, column `floor_plans.furniture`): `{auto, rooms: {"<room name>":
[items]}}`, sizes in feet. `furniture_spec` cleans what the AI sends (`find_piece` matches words against
`PIECES` with aliases, and a plain "chair"/"table"/"sink" by `room_kind`; bed sizes, color and wood words);
the prompt text is `FURNITURE_FORMAT` in `ai_planning_service.py` — keep the two in step. `auto: true`
furnishes every room *not* listed by its kind (`auto_items`); a listed room gets exactly its items. Like
the exterior: new versions carry it over (renamed with `rename_rooms`, pruned to rooms that still exist),
and a refine with `scope: "furniture"` updates the current version in place, the AI returning only the
rooms that change (`merge_furniture`). `build_furniture` places the pieces (a `RoomSpace` per room):
nothing in front of a doorway (0.9 m kept clear; openings carry a `kind` — door, open, bay, window — set in
`vr_geometry_service`), nothing taller than a window sill in front of a window (`_wall_height`: a bed counts
only its mattress, counters just under the sill), big pieces against the wall with the longest free run,
then what goes with them (nightstands by the bed, coffee table before the sofa, chairs round a table as
part of the table, stools at the island), then corners and rugs. `x`/`z` (feet from the room's front-left
corner) place a piece exactly. Pieces are low-poly meshes **in metres** (base at y = 0, front toward +z,
cached per kind/size/colors and shared), instanced with `scale` 1 in `geometry.furniture` (`meshes`,
`pieces` with a plan `outline` for the dashboard, `models` for photo models); what didn't fit (unless it was
only auto furniture) goes to `geometry.notes`. Headset side: `FurnitureBuilder.kt` (through
`MeshInstances.kt`, which `ExteriorBuilder` uses for plants too); dashboard: outlines in `FloorPlanView.vue`.

### VR app — Kotlin + Meta Spatial SDK (`construction-quest/app/src/main/java/.../`)
- `ImmersiveActivity.kt` — main activity; orchestrates the whole pipeline: voice capture, the
  transcribe/confirm → floor plan build → transcribe/confirm → image/review sequence, WebSocket wiring,
  and panel display.
- `HouseGenerator.kt` — fetches geometry and builds entities. Walls are placed at `start.y + height/2`
  (pieces above doors/windows float); doors are drawn as an open frame (two jambs + head), never a slab,
  since the backend already left a hole in the wall. **Thread rule:** `fetchVRGeometry(projectId)` /
  `fetchVRGeometryFromPrompt(...)` do the HTTP call on an **IO thread**; `buildFromGeometry(...)`
  calls `Entity.create()` and **must run on the main/UI thread** (`runOnUiThread { ... }`).
  `buildFromGeometry` calls `clearAllEntities()` first, so rebuilding replaces the house rather than
  stacking a second one; entity handles live in `roomEntities`/`doorEntities`/`windowEntities` (the
  outside in `ExteriorBuilder`) and anything you create must be tracked there or it leaks across rebuilds.
- **Eye height**: the player is lifted to a 6 ft person's eye level: `placeViewer` (spawn,
  teleport, return to the panels) raises the view origin so the eyes are at `EYE_HEIGHT_M` (1.71 m, a 6 ft
  person) × `SCALE` above the floor, measured from the real head height at that moment (sitting or
  standing gives the same view); walking keeps that lift and follows `HouseGenerator.floorLevelAt`
  (floor inside, the yard's `GROUND_TOP` outside). Panels go through `panelY(y)` so they keep their height
  relative to the head; `clearHouse` drops the lift.
- `ProgressBar.kt` — two-entity (background + fill) VR progress bar driven by the image-progress WS.
- `PanelActivity.kt` — WebView-backed confirmation/info panels (HTML rendered in VR).
- Networking is OkHttp (HTTP + WebSocket).

### Project controls, CRM and the AI copilot (backend)
- **Construction plan in pm-mcp.** Phases, tasks, permits, inspections, budget lines, expenses and change orders
  are **not in Postgres**: they live in pm-mcp (`/development/pm-mcp`, an MCP server shared with AI agents and
  other apps), reached over HTTP by `services/pm_client.py` (a small JSON-RPC client; the `mcp` package needs a
  newer Starlette than this FastAPI). `start_all.sh` starts pm-mcp on :8765 (`PM_MCP_URL`, board file
  `~/.local/share/pm-mcp/pm.db`). A project gets its pm-mcp project on first use (`ensure_pm_project`, stored in
  `projects.pm_project_id`, linked in pm-mcp as `vr-construction:<id>`); deleting a project archives it there.
  Each request loads the plan once (`load_plan` → `export_project`) into a `Plan`; phases are pm-mcp milestones,
  tasks pm-mcp tasks, the rest pm-mcp records (`budget_item` with `data.line` `phase_budget` or `expense`,
  `change_order`, `permit`, `inspection`). Errors: `PMError` (pm-mcp refused; 404/409) and `PMUnavailable` (503;
  the overview and punch list still answer with `pm_available: false`). The old tables
  (`construction_phases`, `tasks`, `permits`, `inspections`, `budget_items`, `budget_categories`,
  `change_orders`) are still in the database but unused; punch items' `phase_id` and crew/equipment
  assignments' `task_id` hold pm-mcp ids.
- **Project controls** (`api/v1/project_controls.py` → `services/project_controls_service.py`), per project:
  `GET .../overview` (schedule/budget/compliance summaries, floor plan brief, linked clients, `attention` list),
  `.../schedule` (+ `POST .../schedule/baseline {start_date}`, phases/tasks CRUD), `.../budget` (earned value),
  `.../expenses`, `.../change-orders`, `.../compliance` (+ permits/inspections CRUD), `GET
  .../construction-templates` and `POST .../construction-plan {template, start_date?}` (lay a pm-mcp template
  into the plan). The AI plan's phases and tasks go to pm-mcp from `_save_project` (`import_ai_phases`) after the
  project commits; if pm-mcp is down the project is still saved (`construction_plan: "pm_unavailable"`). The plan
  here is **sequential**: tasks this app adds are chained with pm-mcp dependencies (`_chain_predecessor`; deleting
  one reconnects the chain), so pm-mcp's scheduler lays them end to end in calendar days (`workdays_only` false);
  template plans keep their own dependencies. A task's `planned_end` is exclusive (pm-mcp's `planned_finish` + 1).
  Progress is **earned with the 50/50 rule** (half a task's duration when it starts, the rest when completed);
  phase progress/status are derived from the tasks on every read. BAC = budget lines (or the plan's estimate) +
  approved change orders; a phase's budget is its lines' total (`_set_phase_budget` keeps an own line for what
  estimators' itemised lines don't cover); EV = phase budget × progress; AC = actual costs on budget lines; PV/SPI
  exist only once the schedule has planned dates. **Gates**: a task with `requires_inspection` is a pm-mcp
  `inspection` task with a linked inspection record; completing it is refused (409) until the inspection passes.
  Recording `passed` completes it, `failed`/`partial` adds a correction task it waits on (the response carries
  `completed_task` / `correction_task`). Permit and inspection statuses are pm-mcp's
  (`PERMIT_STATUSES`, `INSPECTION_STATUSES`); approving a template's permit completes its permit task.
- **Punch list** (table `punch_items`, routes in `project_controls.py`): `GET .../punch-list` (items open-first by
  priority and due date, `summary`, the current floor plan's `rooms`, `trades`), `POST .../punch-items`,
  `PATCH`/`DELETE .../punch-items/{id}`. Numbered `PL-001`… per project; status `open → in_progress → ready →
  closed` (closing stamps `closed_at`, reopening clears it). The overview carries `punch_list` (summary) and adds
  **one** attention line for all overdue items and one for items ready for sign-off; the copilot snapshot sees it.
  Punch items stay in Postgres (they belong to floor-plan rooms) and are copied one way to pm-mcp
  `punch_item` records (`sync_punch_item`, `punch_items.pm_record_id`), best effort.
- **Crew & equipment** (`api/v1/resources.py`): the global `labor_resources` / `equipment` tables, each on at
  most one project.
- **CRM** (`api/v1/crm.py` → `services/crm_service.py`, tables `clients`, `client_activities`): pipeline
  `STAGES` with a usual win probability each (a stage change logs a `stage_change` activity and resets it
  unless one is given); contact activities update `last_contact_at`; `POST /crm/clients/{id}/project` starts
  (or links) the client's project; `GET /crm/pipeline` = per-stage totals, weighted forecast, follow-ups due.
  Deleting a project unlinks its clients.
- **AI** (`services/ai_assistant_service.py`): `complete_json` is a small Groq→Ollama→Gemini chain for short
  JSON answers (not plans; 60 s budget) using `planning_service`'s clients. Copilot `POST /assistant/chat`,
  client insights `POST /crm/clients/{id}/ai/insights` (saved on the client), email drafts `.../ai/draft`
  (never sent). Every prompt carries a DB snapshot and must not invent facts; `budget_reading` states what
  CPI/SPI/EAC mean because models misread the signs. Copilot `actions` are filtered by `clean_actions` to ones
  that point at real phases/clients; the dashboard asks before running one. Tests replace `complete_json`.

### Dashboard — Vue 3 + Quasar + Pinia (`backend-core/dashboard`)
Project-management and CRM UI around the floor plan. Vite + TypeScript (`npm run build` runs `vue-tsc`
first, so type errors fail the build). Everything comes from the API — no seeded or localStorage data
(localStorage only remembers the selected project, theme and CRM view).
- `MainLayout.vue`: project switcher (the **selected project** is `projects.currentProject`; pages follow it
  through `composables/useProjectData`), attention bell (overview `attention` + CRM follow-ups), copilot drawer
  (`components/ai/AiCopilotWidget.vue`), `NewProjectDialog` (AI plan via `/planning/generate-project`, or blank).
- Pages: Overview (`HomeView`), Design studio (`DesignStudioView`, wraps `FloorPlanView`), CRM (`CrmView`:
  kanban/table, `ClientDetailDrawer`, `AiOutreachModal`; `?client=ID&draft=purpose` deep-links), Schedule
  (`TimelineView` + `schedule/GanttChart`), Budget, Materials (BOM from `materials`, CSV export), Crew &
  equipment, Permits & inspections, Punch list (`PunchListView`, store `punchList`), plant/furniture model libraries.
- `FloorPlanView.vue` draws the selected project's layout (rooms, doorways, windows, entry) as SVG from
  `GET /projects/{id}/generate-vr`, using each room's `bounds`; the street side is drawn at the bottom. For a
  project with a floor plan it also edits it (house name, footprint, split sizes, room names, two-way doorways,
  entry → `PUT .../floor-plan`), applies typed changes (`.../floor-plan/refine`), lists versions with Restore,
  and shows the accepted rendering. It emits `changed` on every new version (the studio offers to log a change
  order) and exposes `reload` / `refineWith(text)`.
- **Load to VR** is only the headset WebView bridge `Android.loadProject(id)` (`composables/useLoadToVr`).
- Breakpoints are custom (`quasar-variables.sass`: md = 1024–1440): use `col-md-*` for desktop layouts —
  `col-lg-*` only applies above 1440 px. Colors/surfaces are CSS tokens in `App.vue` (light + dark); status
  badge colors are in `utils/status.ts`; charts (`components/charts/BarChart.vue`) use a validated
  3-slot palette per mode.

## Pipeline (the path through the code)
The headset runs a **two-prompt voice flow**, a state machine on `VoiceState` in `ImmersiveActivity.kt`:
**floor plan first, then the 2D image** — the user describes the look while standing inside the house.

1. **Prompt 1 — floor plan.** Hold Button A → record → `POST /api/v1/voice/transcribe` (Whisper) →
   WebView confirm panel (A confirm / B retry).
2. `onConfirmPrompt1` → `fetchVRGeometryFromPrompt(text, null)` →
   `POST /api/v1/planning/generate-vr-from-prompt` on an IO thread (which now **saves the house as a project**
   with floor plan v1, like `/generate-project`; the geometry carries its `project_id`/`project_name`) → `runOnUiThread { buildFromGeometry(...) }`.
   The player is moved to the spawn point, locomotion and room labels turn on, and `panelAnchor` is set to
   the spawn point so the prompt panel, progress bar and review panel follow the player into the house.
   On failure the flow returns to `IDLE`.
3. **Prompt 2 — house look.** Same record/transcribe/confirm, from `READY_FOR_PROMPT2`.
4. `onConfirmPrompt2` → `POST /api/v1/image/generate` → `WS /api/v1/ws/image-progress/{id}`; the
   ProgressBar animates (with a stall watchdog) until the image arrives. On failure the flow returns to
   `READY_FOR_PROMPT2` and the house is kept.
5. **Review** on a large panel beside the prompt panel: **Accept** (A) moves the image to a grabbable
   walking panel (`WALKING`); **Edit Prompt** (B) deletes the image and re-records prompt 2;
   **Start Over** deletes the image and calls `clearHouse()` back to step 1.

**House sign and voice refinement.** `enterHouse` records the house's `project_id`, name and floor-plan
version from the geometry and shows a "NOW VIEWING" sign (`house_sign` panel) above the prompt panel.
In a saved house, from `READY_FOR_PROMPT2` or `WALKING`, holding the **right grip** records a floor-plan
change (`RECORDING_REFINE` → `CONFIRMING_REFINE` → `REFINING_GEOMETRY`, transcription phase 3); confirming
posts it to `/floor-plan/refine` and rebuilds the house from the new version, returning to the state it
started from (the walking image is re-spawned). Accepting an image links it to the floor plan.

The two prompts are independent: neither is sent as grounding for the other (`image_prompt` on
`generate-vr-from-prompt` is still supported but not used by the headset).

**Button B is overloaded** once a house is loaded: Retry / Edit Prompt during confirm and review, and
"clear house" otherwise. Clearing is edge-triggered and only allowed from `IDLE`, `READY_FOR_PROMPT2`
or `WALKING` (sampled before `handleVoiceInput` runs), so a B held through Retry can't also wipe the house.

**Second entry point — dashboard-driven:** "Load to VR" in `HomeView.vue` calls the WebView bridge
`Android.loadProject(projectId)` and loads **the house only** (no picture, so the grip works at once).
The headset side is `loadProjectById(projectId, generationId?)` in `ImmersiveActivity.kt`: it is ignored
while recording, transcribing or generating; otherwise it **replaces** any loaded house (`clearHouse()` +
`enterHouse()`). `POST /api/v1/projects/{id}/load-to-vr` (starts an image and returns its `generation_id`)
and `Android.loadProjectWithImage(projectId, generationId)` still exist but the dashboard no longer uses
them; with a generation id the headset follows that image into the normal review step. `ImmersiveActivity` opens the
dashboard itself in a VR WebView at `BuildConfig.DASHBOARD_URL`.

**Stale results are dropped:** a generation whose POST returns or whose `completed` message arrives
after the flow left `GENERATING_IMAGE` (watchdog abort, a different generation) is deleted, not shown.
Progress bars are dismissed via `dismissProgressBar(delay)`, which captures the bar it was called for.

Key endpoints for the headset: `POST /api/v1/voice/transcribe`,
`POST /api/v1/planning/generate-vr-from-prompt` (saves a project), `POST /api/v1/projects/{id}/floor-plan/refine`, `POST /api/v1/image/generate`,
`WS /api/v1/ws/image-progress/{id}`, `GET /api/v1/projects/{id}/generate-vr` (dashboard path),
`WS /api/v1/ws/room/{roomId}`. Interactive docs at `/docs`. `POST /api/v1/planning/generate-project`
(full plan with phases, tasks, materials, cost, timeline) and `POST /api/v1/designs/{id}/generate-vr`
also exist; all geometry routes share `vr_geometry_service.py`.

## Gotchas
- The Quest reaches the backend by **LAN IP**, never `localhost`. If geometry/voice calls fail from
  the headset, check the hard-coded server IP in the Kotlin source matches the machine running uvicorn.
- Uvicorn must bind `0.0.0.0` (the restart script does); binding `127.0.0.1` makes it invisible to the headset.
- Use `llama3.1:8b` exactly on the Ollama path — `llama3.1:latest` was getting OOM-killed.
- `SERVER_URL` / `WS_URL` / `DASHBOARD_URL` (and `COLLAB_TOKEN`) are `BuildConfig` fields generated in
  `app/build.gradle.kts` from `serverHost` / `collabToken` in `construction-quest/gradle.properties`.
  Change `serverHost` (or pass `-PserverHost=…`) when the host IP changes; the dashboard's `.env`
  (`VITE_API_BASE_URL`, `VITE_WS_URL`) holds the same IP and must be changed too.
- Provider fallback hides failures: a plan that looks wrong may have come from Ollama or Gemini rather
  than Groq. Check the log line naming the planner before debugging prompt/schema issues.
- The repo root holds many one-off `*.md` fix logs and `test_*.py` scratch scripts from past debugging
  sessions; they are history/notes, not the canonical test suite (which is `backend-core/backend/tests/`).
