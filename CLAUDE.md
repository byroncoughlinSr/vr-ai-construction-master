# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

End-to-end pipeline that turns a spoken prompt into a walkable VR house on Meta Quest 2/3:
voice → Whisper transcription → LLM construction plan → Stable Diffusion rendering →
3D geometry → Meta Spatial entities the user walks through. Three deployable parts talk over
HTTP/WebSocket; there is no shared code between them — the contract is the JSON on the wire.

```
construction-quest (Kotlin/Quest)  ──HTTP/WS──►  backend-core/backend (FastAPI)  ◄──HTTP──  backend-core/dashboard (Vue 3)
```

- Backend server: `http://192.168.4.249:8000`  (LAN IP — the Quest must reach this, not localhost)
- Dashboard dev server: `http://localhost:3001` (Vite binds `0.0.0.0`; the Quest loads it by LAN IP)
- WebSocket base: `ws://192.168.4.249:8000/api/v1/ws`

## Commands

### Backend (`backend-core/backend`)
```bash
./start_all.sh                    # from repo root: backend (:8000, log → backend/backend.log) + dashboard (:3001); Ctrl+C stops both
./restart_backend.sh              # from repo root: kills port 8000, activates venv, runs uvicorn --reload
source venv/bin/activate          # the venv lives in backend-core/backend/venv
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload   # manual run (must bind 0.0.0.0 so Quest can reach it)
pytest                            # all backend tests
pytest tests/test_api.py          # one file
pytest tests/test_api.py::test_name   # one test
alembic revision --autogenerate -m "msg"  # new migration
alembic upgrade head                      # apply migrations (the backend also runs them on startup)
python -m scripts.seed_example_floor_plan # migrate + add the example house "Maple Hollow Cottage"
docker compose up -d postgres pgadmin   # DB only — the backend container would take port 8000 from
                                        # the native uvicorn (docker-compose.prod.yml has profiles)
```
There is no `pytest.ini`/`conftest.py` — run `pytest` from `backend-core/backend` with the venv
(Python 3.12, full `requirements.txt`) active. Tests use in-memory SQLite: each test module installs
its `get_db` override in a fixture and removes it afterwards — don't set `app.dependency_overrides`
at import time, or modules clobber each other's database. `app/services/__init__.py` imports lazily,
so `vr_geometry_service` loads without torch; `test_vr_geometry.py` and `test_planning_service.py`
make no network calls. `test_compel_integration.py` needs a GPU and real models (its async tests are skipped).
Config comes from `.env` (copy `.env.example`); `app/config.py` is the Pydantic settings source of truth.

**LLM provider chain** (`ai_planning_service.py`, in priority order):
1. **Groq** — the primary planner. `GROQ_API_KEY` + `GROQ_MODEL` (default `openai/gpt-oss-120b`),
   called with `response_format={'type':'json_object'}`.
2. **Ollama** — fallback. Runs **natively, not in Docker** (Docker Ollama was OOM-killed); model
   `OLLAMA_MODEL=llama3.1:8b` exactly; `OLLAMA_URL=http://localhost:11434` when uvicorn runs natively
   (the Docker bridge IP only when the backend is containerised). Unlike Groq/Gemini, Ollama is re-probed
   (3 s timeout) at most every 30 s while down, and only when the chain reaches it, so starting it
   (`sudo systemctl start ollama`) needs no backend restart.
   See `QUICK_START.md` / `NATIVE_OLLAMA_SETUP.md`.
3. **Gemini** — last-resort fallback, `GEMINI_API_KEY`.

A missing key silently demotes to the next provider. The chain moves on when a provider errors, times out,
**or returns output that can't be parsed into a plan**; all of it shares one `PLANNING_TIMEOUT_SECONDS`
budget (200 s, below the headset's 240 s `PLAN_CALL_TIMEOUT_S`). The log line `🧠 Plan generated by <name>`
says which planner actually ran.

## Architecture

### Backend — FastAPI (`backend-core/backend/app`)
- `main.py` mounts all routers under `/api/v1/*` and wires middleware (rate limiting via slowapi,
  CORS, gzip, request-ID logging). Router prefixes: `image`, `planning`, `projects`, `designs`,
  `materials`, `voice`, `ws`.
- `api/v1/` = HTTP/WS surface; `services/` = the actual AI + geometry logic; `models/` SQLAlchemy,
  `schemas/` Pydantic. Routes stay thin and delegate to services.
- **AI services** (`services/`): `ai_planning_service.py` (Groq→Ollama→Gemini → phases, tasks,
  materials, cost, timeline, image prompt), `ai_image_service.py` (Stable Diffusion + compel,
  CUDA when available else CPU), and `vr_geometry_service.py` (rooms → floor/wall/ceiling/door/window
  vertices).
- **Never trust raw LLM output as JSON.** `ai_planning_service.py` runs everything through
  `_parse_structured_plan` → `_extract_and_repair_json` / `_clean_json_string`: it strips code fences,
  fixes trailing/missing commas and Python literals, and closes truncated objects/arrays. If you add a
  provider or change the plan schema, route it through that pipeline. Strategy 1 parses the extracted JSON
  **as-is first** and only runs the regex repairs (`_clean_json_string`) if that fails — the repairs work
  on raw text and corrupt valid strings (`"Bedroom 2"` → `"Bedroom 2,"`). Background in `JSON_PARSING_FIX.md`.
- **Image generation** (`ai_image_service.py`): one shared pipeline (`get_image_service()`), one generation
  at a time behind an `asyncio.Lock`. Compel runs with `truncate_long_prompts=False` and pads the
  prompt/negative embeddings to the same length, so long voice descriptions are not cut at 77 tokens.
  `POST /image/generate` bounds width/height (256–1024, multiple of 8), steps (1–100) and guidance.
  Background jobs go through `image_jobs.start_image_generation` → `background.run_in_background`
  (holds a strong task reference); results/errors are kept 15 min for late WebSocket clients.
- DB is PostgreSQL via SQLAlchemy 2.0; migrations with Alembic (`alembic.ini`, `alembic/`). Migrations are the
  only thing that creates tables; revision `9a4e6c1f2b83` rebuilt the budget/permit/inspection/document tables,
  which the initial migration had created with an older layout than the models. After changing a model,
  autogenerate a migration and check `compare_metadata` comes back empty.
- **Floor plans** (`models/floor_plan.py`, `services/floor_plan_service.py`): the `floor_plans` table holds
  versioned plans per project — `name` (the house name), `layout` tree and `rooms` (feet), `change_type`
  (`generated` / `edited` / `refined` / `example`), `change_note`, `source`, and the accepted `image_url`.
  Every change inserts the next version; the highest is current and is what `GET /projects/{id}/generate-vr`
  builds (via `geometry_for_project`, which falls back to the old `ai_generations` plan, then phase names, for
  projects without one). Geometry carries `floor_plan: {id, version, name, image_url}`. Routes:
  `GET /projects/{id}/floor-plan(s)`, `PUT /projects/{id}/floor-plan` (dashboard edit; renames the project
  too; 422 if unbuildable), `POST /projects/{id}/floor-plan/refine` (`{instruction}` → planner chain via
  `refine_floor_plan`, prompt in `_build_refine_prompt` — keep it in step with `_build_planning_prompt`),
  `PUT /projects/{id}/floor-plan/image` (link an accepted render). `ai_generations.source` now records the
  real provider (it used to default to "ollama"). The example plan lives in `services/example_floor_plans.py`.

### VR geometry — the cross-language contract that breaks silently
`vr_geometry_service.py` builds the JSON that `HouseGenerator.kt` turns into 3D boxes. Three
constants **must** stay in sync across the language boundary or the house develops visible seams:
- `WALL_T = 0.1` (half wall thickness) must equal `WALL_HALF_THICKNESS_M = 0.1f` in `HouseGenerator.kt`.
  Every Kotlin box goes through `centeredBox(size)` (`Boxes.kt`): the SDK's `Box(min, max)` takes two
  corners, and passing one vector puts the box beside its entity instead of around it.
- `FT_TO_M = 0.3048` — the AI returns dimensions in **feet**; the VR world is **metres** (1 unit = 1 m).
  Conversion happens backend-side; Kotlin consumes metres directly.
- `SCALE = 2.0f` in `HouseGenerator.kt` — **every** position, dimension and spawn point from the JSON is
  multiplied by it on the Kotlin side. Anything you add to the geometry JSON must be scaled too, or it
  lands at half size / half distance relative to the rest of the house.

**Layout is a nested-split tree** the AI returns as `project_structure.layout`: a footprint
(`length` along x, `width` along z, street side at z = 0) recursively divided by `"split": "x"|"z"` into
`parts`, each with a relative `size` and either a `room` name or another split
(`layout_rects_from_tree`). Part sizes are rescaled to fill their parent, with a `MIN_PART` floor, so
rooms always tile the footprint with no gaps or overlaps. `project_structure.rooms` then only supplies
height, materials and `connects_to`. `layout.entry` names the room that gets the front door (it becomes
room id 1). The prompt in `_build_planning_prompt` describes this format — change both together.
If the tree is missing or malformed (`LayoutError`), it falls back to the old grid:
`compute_packed_positions` packs rooms 3 per row in list order, rows share their max depth, and room 0
is the entry. `geometry.metadata.layout` says which one ran (`"split"` / `"grid"`).

Doorways (`plan_connections`): a requested connection becomes a door only if the two rooms share at
least `DOOR_W + 2·EDGE_MARGIN` of wall (`find_shared_walls`); then doors are added until every room is
reachable from the entry, preferring hallways/living spaces. The front door goes on the entry's outside
wall (street side first, then sides, then back) and `spawn_position` is 3 m outside it. Windows go on the longest exterior stretch
(none in hallways/closets, small ones in bathrooms). Openings are **cut out of the walls backend-side**:
every wall on the opening's line (i.e. both rooms' walls) is split into pieces around it, and each
piece's `start.y` is its base height (0, or the door/window top for headers). Rotation values are sent in
**degrees** in the JSON — `HouseGenerator.kt` must `Math.toDegrees(atan2(...))` because
`Quaternion(...)` expects degrees, and must apply each element's `rotation` field. The history of
seam/rotation bugs and the exact fixes is documented in `claude.md` (despite the name, it is a
fix-notes doc, not guidance) and `LOAD_TO_VR_FIX.md` — read these before touching geometry.

### VR app — Kotlin + Meta Spatial SDK (`construction-quest/app/src/main/java/.../`)
- `ImmersiveActivity.kt` — main activity; orchestrates the whole pipeline: voice capture, the
  transcribe/confirm → floor plan build → transcribe/confirm → image/review sequence, WebSocket wiring,
  and panel display.
- `HouseGenerator.kt` — fetches geometry and builds entities. Walls are placed at `start.y + height/2`
  (pieces above doors/windows float); doors are drawn as an open frame (two jambs + head), never a slab,
  since the backend already left a hole in the wall. **Thread rule:** `fetchVRGeometry(projectId)` /
  `fetchVRGeometryFromPrompt(...)` do the HTTP call on an **IO thread**; `buildFromGeometry(...)`
  calls `Entity.create()` and **must run on the main/UI thread** (`runOnUiThread { ... }`).
  `buildFromGeometry` calls `clearAllEntities()` first, so rebuilding replaces the house rather than
  stacking a second one; entity handles live in `roomEntities`/`doorEntities`/`windowEntities` and
  anything you create must be tracked there or it leaks across rebuilds.
- `ProgressBar.kt` — two-entity (background + fill) VR progress bar driven by the image-progress WS.
- `PanelActivity.kt` — WebView-backed confirmation/info panels (HTML rendered in VR).
- Networking is OkHttp (HTTP + WebSocket).

### Dashboard — Vue 3 + Quasar + Pinia (`backend-core/dashboard`)
Management UI for projects, materials, generated images, and run history. Vite + TypeScript
(`npm run build` runs `vue-tsc` first, so type errors fail the build). `FloorPlanView.vue` on the home
page draws the selected project's layout (rooms, doorways, windows, entry) as SVG from
`GET /projects/{id}/generate-vr`, using each room's `bounds`; the street side is drawn at the bottom. For a
project with a floor plan it also edits it (house name, footprint, split sizes, room names, two-way doorways,
entry → `PUT .../floor-plan`), applies typed changes (`.../floor-plan/refine`), lists versions with Restore,
and shows the accepted rendering.

## Pipeline (the path through the code)
The headset runs a **two-prompt voice flow**, a state machine on `VoiceState` in `ImmersiveActivity.kt`:
**floor plan first, then the 2D image** — the user describes the look while standing inside the house.

1. **Prompt 1 — floor plan.** Hold Button A → record → `POST /api/v1/voice/transcribe` (Whisper) →
   WebView confirm panel (A confirm / B retry).
2. `onConfirmPrompt1` → `fetchVRGeometryFromPrompt(text, null)` →
   `POST /api/v1/planning/generate-vr-from-prompt` on an IO thread (which now **saves the house as a project**
   with floor plan v1, like `/generate-project`; the geometry carries its `project_id`/`project_name`) → `runOnUiThread { buildFromGeometry(...) }`.
   The player is moved to the spawn point, locomotion and room labels turn on, and `panelAnchor` is set to
   the spawn point so the prompt panel, progress bar and review panel follow the player into the house.
   On failure the flow returns to `IDLE`.
3. **Prompt 2 — house look.** Same record/transcribe/confirm, from `READY_FOR_PROMPT2`.
4. `onConfirmPrompt2` → `POST /api/v1/image/generate` → `WS /api/v1/ws/image-progress/{id}`; the
   ProgressBar animates (with a stall watchdog) until the image arrives. On failure the flow returns to
   `READY_FOR_PROMPT2` and the house is kept.
5. **Review** on a large panel beside the prompt panel: **Accept** (A) moves the image to a grabbable
   walking panel (`WALKING`); **Edit Prompt** (B) deletes the image and re-records prompt 2;
   **Start Over** deletes the image and calls `clearHouse()` back to step 1.

**House sign and voice refinement.** `enterHouse` records the house's `project_id`, name and floor-plan
version from the geometry and shows a "NOW VIEWING" sign (`house_sign` panel) above the prompt panel.
In a saved house, from `READY_FOR_PROMPT2` or `WALKING`, holding the **right grip** records a floor-plan
change (`RECORDING_REFINE` → `CONFIRMING_REFINE` → `REFINING_GEOMETRY`, transcription phase 3); confirming
posts it to `/floor-plan/refine` and rebuilds the house from the new version, returning to the state it
started from (the walking image is re-spawned). Accepting an image links it to the floor plan.

The two prompts are independent: neither is sent as grounding for the other (`image_prompt` on
`generate-vr-from-prompt` is still supported but not used by the headset).

**Button B is overloaded** once a house is loaded: Retry / Edit Prompt during confirm and review, and
"clear house" otherwise. Clearing is edge-triggered and only allowed from `IDLE`, `READY_FOR_PROMPT2`
or `WALKING` (sampled before `handleVoiceInput` runs), so a B held through Retry can't also wipe the house.

**Second entry point — dashboard-driven:** the dashboard calls
`POST /api/v1/projects/{id}/load-to-vr` (starts the image in the background and returns its
`generation_id`); `HomeView.vue` then calls the WebView bridge `Android.loadProjectWithImage(projectId,
generationId)` (falling back to `Android.loadProject(projectId)`). The headset side is
`loadProjectById(projectId, generationId?)` in `ImmersiveActivity.kt`: it is ignored while recording,
transcribing or generating; otherwise it **replaces** any loaded house (`clearHouse()` + `enterHouse()`)
and, with a generation id, follows that image into the normal review step. `ImmersiveActivity` opens the
dashboard itself in a VR WebView at `BuildConfig.DASHBOARD_URL`.

**Stale results are dropped:** a generation whose POST returns or whose `completed` message arrives
after the flow left `GENERATING_IMAGE` (watchdog abort, a different generation) is deleted, not shown.
Progress bars are dismissed via `dismissProgressBar(delay)`, which captures the bar it was called for.

Key endpoints for the headset: `POST /api/v1/voice/transcribe`,
`POST /api/v1/planning/generate-vr-from-prompt` (saves a project), `POST /api/v1/projects/{id}/floor-plan/refine`, `POST /api/v1/image/generate`,
`WS /api/v1/ws/image-progress/{id}`, `GET /api/v1/projects/{id}/generate-vr` (dashboard path),
`WS /api/v1/ws/room/{roomId}`. Interactive docs at `/docs`. `POST /api/v1/planning/generate-project`
(full plan with phases, tasks, materials, cost, timeline) and `POST /api/v1/designs/{id}/generate-vr`
also exist; all geometry routes share `vr_geometry_service.py`.

## Gotchas
- The Quest reaches the backend by **LAN IP**, never `localhost`. If geometry/voice calls fail from
  the headset, check the hard-coded server IP in the Kotlin source matches the machine running uvicorn.
- Uvicorn must bind `0.0.0.0` (the restart script does); binding `127.0.0.1` makes it invisible to the headset.
- Use `llama3.1:8b` exactly on the Ollama path — `llama3.1:latest` was getting OOM-killed.
- `SERVER_URL` / `WS_URL` / `DASHBOARD_URL` (and `COLLAB_TOKEN`) are `BuildConfig` fields generated in
  `app/build.gradle.kts` from `serverHost` / `collabToken` in `construction-quest/gradle.properties`.
  Change `serverHost` (or pass `-PserverHost=…`) when the host IP changes; the dashboard's `.env`
  (`VITE_API_BASE_URL`, `VITE_WS_URL`) holds the same IP and must be changed too.
- Provider fallback hides failures: a plan that looks wrong may have come from Ollama or Gemini rather
  than Groq. Check the log line naming the planner before debugging prompt/schema issues.
- The repo root holds many one-off `*.md` fix logs and `test_*.py` scratch scripts from past debugging
  sessions; they are history/notes, not the canonical test suite (which is `backend-core/backend/tests/`).
